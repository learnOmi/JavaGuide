# 07-阅读续读（上次阅读位置恢复）-设计与实施记录

## 1. 背景与目标

问题：重启开发服务后重新打开站点，无法回到上次离开的页面与内容位置。

用户澄清："书签"指的是**自动续读**（记住并恢复上次读到哪），不是收藏列表。经确认的三项边界：

| 决策项 | 结论                                                            |
| ------ | --------------------------------------------------------------- |
| 范围   | 只做自动续读；不含编辑器状态（编辑器已有自己的草稿/偏好持久化） |
| 行为   | 只给入口，**点击才恢复**，不自动跳转                            |
| 存储   | 纯本地（localStorage），不引入服务端                            |

目标：以最小侵入接入，不改变既有阅读行为；恢复失败或不适用时静默退化为"什么都不做"。

## 2. 方案与关键取舍

### 2.1 为什么不用 `savedPosition`

vue-router 的 `scrollBehavior` 第三个参数 `savedPosition` 只在 SPA 内前进/后退时由路由器填充；**整页刷新时为 `undefined`**。而用户的场景恰恰是"重启项目 → 重新打开页面"，属于整页加载，因此 `savedPosition` 必然落空。这是本功能必须自建存储的根本原因。

### 2.2 为什么用"锚点 + 进深"而不是绝对像素

本站正文含懒加载图片、异步 Mermaid、代码高亮，页面高度在加载完成后仍持续变化。若记录绝对 `scrollY`（例如 4200），下次打开时上方内容可能只铺开 3000，落点必然错位。

因此记录形态为：

```
anchor: 最近的上方标题 id（h2/h3/h4 中带 id 者）
offset: scrollY + navOffset - absTop(anchor)     // 相对该标题的"已读进深"
```

恢复时按**最新布局**重算：

```
targetScrollY = absTop(anchor) - currentNavOffset() + offset
```

两者严格互逆（同一 `navOffset` 下）。锚点元素已不存在（页面改版/删除）时返回 `null`，放弃恢复。

### 2.3 为什么不用 IntersectionObserver / 哈希

- 主题自身已有 hash scroll-spy 链路（滚动 → 改写 `location.hash` → vue-router `scrollBehavior` 滚回锚点），这是本站 `SCROLL_GUARD_*` 存在的原因。再叠加一套哈希机制会互相打架。
- IntersectionObserver 只在元素进出视口时回调，拿不到"精确断点"，不适合做恢复。

### 2.4 沉浸模式的偏移修正

`navOffset` 在非沉浸模式为 80px（让标题停在 sticky 导航栏下方），沉浸模式为 0（导航栏已隐藏，多算 80px 会让落点凭空偏下）。`currentNavOffset()` 通过检测 `<html>` 上的 `layout-hidden` 类判定。

### 4.1 偏差：`NAV_OFFSET_PX` 未复用 `SCROLL_SYNC_PAGE_OFFSET_PX`

计划原写"复用 `docEditorState.ts` 的 `SCROLL_SYNC_PAGE_OFFSET_PX`（不新增第二个 80）"。实际实施**刻意不复用**：

`docEditorState.ts` 顶层 `import { pinyin } from "pinyin-pro"`，任何对它的 import 都会把拼音库拖进主包首屏。`ResumeReading` 属于全局挂载组件，不能接受这个代价。

处理方式：在 `readingPosition.ts` **镜像同一约定值**，并在注释中写明"两处若需调整必须同步"。代价是存在一个需要人工同步的重复常量；收益是主包不被拼音库污染。判断：约定值稳定（80 是站点统一"导航栏遮挡"口径），同步成本可忽略，故接受该偏差。

## 5. 组件逻辑编排

```
滚动 / pagehide / visibilitychange(hidden)
      └─> saveCurrent()  ──节流──> capturePosition(route.path, title)
                                        └─> writeSaved()  → localStorage

挂载 / route.path 变化
      └─> refresh()  ──> readSaved()
                ├─ 无记录 / 已 dismiss / 即本次刚恢复的页 → 隐藏
                ├─ pos.path ≠ route.path            → 显示（跨页续读）
                └─ pos.path = route.path            → 仅当"在页顶且不在原位"才显示

点击入口
      └─> restore()
            ├─ bindUserInput()（wheel/touchmove/keydown/pointerdown/mousedown）
            ├─ 跨页则 router.push(pos.path)（失败 → clearSaved + 提示）
            ├─ nextTick()
            ├─ applyWithRetry()：循环重算 target → 收敛或超期才停
            ├─ unbindUserInput()
            └─ resumedPath = pos.path（本次会话不再为它弹提示）
```

恢复期间 `restoring = true`：屏蔽保存写入与可见性重算，避免自己打断自己。

### 6.1 修复的缺陷：恢复过早停手导致 447px 漂移

初版 `applyWithRetry` 的停止条件是 `document.documentElement.scrollHeight >= pos.docHeight`。实测发现：页面在"总高刚够"之后，懒加载图片仍继续把锚点往下推，导致恢复停手偏上——**实测 `scrollY=4184`，理想目标 4631，漂移 −447px**（约半个到一个标题间距）。

修复：引入 `RESTORE_SETTLE_CHECKS = 2`，要求**目标坐标连续 2 轮不变**（约 400ms 静默期）且总高不缩水，才认定收敛；同时只在 `|scrollY - target| > 1` 时才写滚动，避免无谓抖动。

复测：`scrollY=4631`，与理想目标 **drift 0px**。修复有效。

## 7. 端口漂移的实测发现

验收启动 dev server 时报 `Port 8080 is in use, trying another one...`，实际监听落到 8081。

排查：8080 被 PID 25812 占用，命令行是 `node .../vuepress.js dev docs`（**无 `--port`**，本机默认 8080），启动于当日 11:59，属于上一轮会话遗留的**旧代码** dev server。

两点结论：

1. localStorage 按 origin 隔离。若端口在 8080/8081 间漂移，记录会落在不同 origin 上，用户会看到"续读莫名失效"。因此 `package.json` 钉死 `--port 8080` 是**功能性必需**，不只是整洁问题。
2. 需如实标注：VuePress/Vite 的 `--port` **不是 strict port**，端口被占用时仍会自动 +1。钉死只能消除"默认漂移"，不能兜底"端口被占"。因此另需一条运维约定：**重启前先确认 8080 没有被上一个 dev server 占着**。

## 8. 已知限制与风险

1. **4s 上限**：极慢网络下内容在 4s 内仍未铺开，落点会有残余漂移。这是"不无限拖住页面"与"落点精确"之间的取舍，选了前者。
2. **锚点失效**：页面改版导致标题 id 变更时放弃恢复（不强行滚到错误位置）。
3. **记录被恢复过程本身刷新**：恢复落位会触发 `scroll` 事件，节流后写出一条按**当前布局**重算的新记录。这是期望行为（保持记录与最新布局一致），但会让"恢复前后记录内容不同"，验收时需注意不要用它反推原始记录。
4. **多标签页互相覆盖**：同一浏览器多个标签同时阅读会共用一个键，后写覆盖前写。当前不处理（单标签阅读为主）。
5. **窄视口（<960px）无入口**：与站内其他悬浮入口（沉浸阅读、编辑入口）保持一致。
6. **沉浸模式下的跨模式一致性**：在非沉浸模式记录、在沉浸模式恢复时，`navOffset` 由 80 变 0，落点会相差 80px。属可接受误差，未做交叉补偿。

## 9. 经验教训

1. **"总高够高"不等于"内容铺开"**：判断懒加载内容是否就绪，盯"目标坐标是否收敛"比盯"文档总高是否达标"可靠。前者直接反映我们真正关心的量。
2. **验收必须用精确数值，不能只看"看起来对"**：子代理的报告只给出"落在文章中部、非页顶"这类定性结论，无法暴露 447px 漂移。改为自算"理想目标 vs 实际落点"的差值后才定位到问题。
3. **验证时警惕"被测系统自己改了数据"**：本功能在恢复后会立刻重写记录，若拿"恢复后的记录"去反推期望值，会得到恒等式（delta 恒为 0）而误判为通过。
4. **环境层故障先读进程自己的日志**：端口冲突不是"配置不生效"，先查 `Get-NetTCPConnection` 找出占用者与它的命令行，再判断是遗留给旧进程。
