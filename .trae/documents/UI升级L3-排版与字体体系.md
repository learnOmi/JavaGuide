# UI 升级 L3：排版与字体体系 — 设计与实施计划

> 阶段：设计（待批准后进入实施）
> 上游：L0 地基、L1 暗色完整化、L2 动效编排层均已完成并归档（记录见 `doc/dev-report/03/04/05`）
> 前置约定：令牌前缀 `--jg-*` 声明在 `docs/.vuepress/styles/palette.scss`；复合值必须写成带引号字符串；样式注入只认 `config.scss` / `palette.scss` / `index.scss` 三个文件。
> 用户决策（2026-10-02）：L3 方向 = **排版与字体体系**。

---

## 一、本期定位：设计系统的第四根支柱

前三根支柱各自补了一个维度：

| 支柱                      | 档位   | 解决的"真相来源"问题                                     |
| ------------------------- | ------ | -------------------------------------------------------- |
| 颜色 / 尺寸 / 圆角 / 阴影 | L0     | 字面量散落 → 令牌                                        |
| 暗色完整化                | L1     | 明暗两套 → map 令牌自动派生                              |
| 动效                      | L2     | 一条过渡刻度 → 按语义角色分档                            |
| **排版（本期）**          | **L3** | **字号/行高散落 + 字体栈两份真相 → 语义刻度 + 单一权威** |

排版是四根里**最贴近本站主业**的一根：这是一个文档站，核心场景就是长文阅读。字号与行高的秩序直接决定"读起来累不累"，比动效更基础。

**本期只做三件事**：字号刻度、行高刻度、字体栈令牌化（含把 FontSwitch 的 7 套预设接上令牌）。

**先划一条硬边界**：主题自身的字号写在 `node_modules` 里，**不可令牌化**。因此本期的收敛范围是**我们自己的层**（`styles/` + `components/`），不试图去改主题内部的 h1–h6、正文行高等。想调整阅读列排版的观感，只能靠往下游覆盖（提高特异性），那是另一件事、风险也更高，本期明确**不做**。

| `components/DocEditor/NewPageDialog.vue`   | 15           | 0.75 / 0.78 / 0.8 / 0.82 / 0.85 / 0.9 / 0.95 |
| `components/DocEditor/DocEditor.vue`       | 9            | 0.7 / 0.75 / 0.78 / 0.8 / 0.82               |
| `components/DocEditor/DeleteDialog.vue`    | 8            | 0.75 / 0.78 / 0.8 / 0.82 / 0.95              |
| `components/DocEditor/FrontmatterForm.vue` | 4            | 0.72 / 0.78 / 0.8 / 0.82                     |
| `components/FontSwitch.vue`                | 4            | 0.75 / 0.8 / 0.85                            |
| `components/unlock/GlobalUnlock.vue`       | 5（+1 图标） | 0.85 / 0.9 / 0.96 / 1 / **1.16**             |
| `components/unlock/UnlockContent.vue`      | 3            | 0.8 / 0.85 / 1                               |
| `components/LazyMermaid.vue`               | 1            | 0.9                                          |
| `components/LayoutToggle.vue`              | 1            | **13px**                                     |
| `styles/index.scss`（正文基准）            | 1            | **16px**                                     |

**问题的形状不是"值太多了"，而是"值挤在一起"**：

```
0.70  0.72  0.75  0.78  0.80  0.82  0.85          1.00  1.16
 └──────── 7 个值全部落在 11.2px ~ 13.6px 的 2.4px 区间内 ────┘
```

7 个互不相同的取值挤在 2.4px 的跨度里——说明它们**不是刻意的层级，而是"每次改一点"的累积**。人眼在这个区间内根本分不出 0.78 / 0.80 / 0.82，维护时也无从判断该抄哪个。这正是 L2 面对 `0.22s / 0.25s` 时遇到的是同一类债，只是这次在字号上。

另外两处是**裸 px**（`13px` / `16px`）：px 不随用户的浏览器字号偏好缩放，是无障碍层面的小缺陷。

### 2.2 行高：仅 4 处文本行高，取值 1.3 / 1.6 / 1.7

| 位置                               | 值  | 用途                |
| ---------------------------------- | --- | ------------------- |
| `FontSwitch.vue:255`               | 1.3 | 密集选项行          |
| `NewPageDialog.vue:545`            | 1.6 | 多行输入框          |

数量不多，但**没有命名**，所以"哪里该用几"只能靠翻代码。

### 2.3 字体栈：一份默认栈被写了两遍，代码字体完全没管

- `styles/palette.scss:20` 的 `$vp-font` 与 `components/fontOptions.ts:38` 的 `SANS_STACK` 是**逐字节相同的同一份系统字体栈**（`system-ui, -apple-system, "Segoe UI", Roboto, ...`）。一个是构建期默认值、一个是运行时预设值——两处真相，改一处另处就漂移。
  这不是新发现：`03-UI风格升级-设计与实施记录.md` 第 64 行已如实记下"内容一致"，当时判定"无需改动"。**本期正是来清这笔账的。**
- `$vp-font-mono`（代码块字体）在 `palette.scss` 里**从未声明**。它现在静默继承主题默认栈（`ui-monospace, "Menlo", "Monaco", "Consolas", ...`，见主题 `templates/palette/font.scss:4`）。也就是说**代码字体不在我们的控制面上**，主题一升级就会跟着变。
- FontSwitch 的 7 套预设（`fontOptions.ts`）是唯一"配了 7 套"的地方，但它们与其他令牌分居两地，不便于统一维护。

### 2.4 不可令牌化边界（实测，非问题）

主题内部字号散落且不可改，抽样：

```
theme: article-item.scss:167  font-size: 15px;
theme: toc.scss:67            font-size: 0.875rem;
theme: page-meta.scss:74      font-size: 13px;
theme: sidebar.scss:19        font-size: 0.94rem;   ...（共 60+ 处）
```

→ **主题内部不在本期范围**。已有的正文基准覆盖（`config.scss` 的 `$theme-color`、`index.scss` 的 body font-size）已是"往下游覆盖"的全部手段。

### 2.5 明确的排除项：图标字形不是文本

两处固定 px 配对其实是**图标字形尺寸**，不是文本层级：

| 位置                              | 声明                                 | 实质                                           |
| --------------------------------- | ------------------------------------ | ---------------------------------------------- |
| `unlock/GlobalUnlock.vue:341-342` | `font-size: 18px; line-height: 28px` | `.close-btn` 的 × 号，按钮框 28×28px           |
| `ClickImagePreview.vue:149-150`   | `font-size: 30px; line-height: 38px` | `.image-preview-close` 的 × 号，按钮框 40×40px |

图标字号必须**锁定 px**（要严丝合缝装进固定尺寸按钮），让它随用户字号缩放反而会破版。→ **不纳入字号刻度**，原样保留。

## 三、核心设计

### 3.1 字号：按「语义刻度」分档，而不是给字面量改名

L2 的结论是"按语义角色分档"；排版同理——**关键不是把散落的值收成少数几个，而是让每个值对应一个可判断的语义角色**。有了角色，下次要加一处字号时才能回答"它属于哪一档"。

推荐刻度（**与 Tailwind 的 `text-*` 刻度对齐**——用户技术栈里就有 Tailwind，这是业界最广为人知的一套比例，便于心算）：

| 令牌           | 值       | ≈px@16 | 语义角色                                       | 收敛的原值                         |
| -------------- | -------- | ------ | ---------------------------------------------- | ---------------------------------- |
| `--jg-fs-xs`   | 0.75rem  | 12     | 徽标、极小标签、角标                           | 0.70 / 0.72 / 0.75 / 0.78          |
| `--jg-fs-sm`   | 0.875rem | 14     | 密集 UI 小字：表单提示、meta、表格头、控件标签 | 0.80\* / 0.82 / 0.85 / 0.90 / 13px |
| `--jg-fs-base` | 1rem     | 16     | UI 正文 / 控件基准                             | 0.95 / 0.96 / 1 / 16px             |
| `--jg-fs-lg`   | 1.125rem | 18     | 次级标题                                       | 1.16 → 见下                        |
| `--jg-fs-xl`   | 1.25rem  | 20     | 面板 / 对话框标题                              | 1.16 → 见下                        |

> \* `0.78` / `0.80` 归 `xs` 还是 `sm` **要逐处看语义**：表格头、角标、极小提示 → `xs`；控件标签、可点击文字 → `sm`。这不是可以机械替换的，也正是收敛必须"带判断"的地方。`1.16rem`（≈18.56px）落两档之间，按用途（`.lock-title` 面板标题）归 `lg`(18px)。

**为什么是这套、而不是"最贴近现状的一套"**：现状值 `0.75 / 0.8125 / 0.875 / 1` 之间的步长只有约 1px，肉眼不可辨，留着 3 档等于留 3 个无法区分的选项——刻度就不成其为刻度。对齐 Tailwind 的代价是 `0.78~0.82` 那批值单点最多变 **+1.3px**（且集中在 `DocEditor/` 这个**仅 dev 生效**的目录，线上零影响，见第六节）。用 ≤1.3px 换一套能心算、能判断的刻度，是划算的。若你更在意"零视觉扰动"，可改用第五节方案 B。

### 3.2 行高：三档命名，覆盖现有全部文本场景

| 令牌              | 值  | 语义角色               | 对应位置                                                                 |
| ----------------- | --- | ---------------------- | ------------------------------------------------------------------------ |
| `--jg-lh-tight`   | 1.3 | 密集单行 / 选项行      | `FontSwitch.vue:255`                                                     |
| `--jg-lh-normal`  | 1.6 | 常规 UI 文本、说明段落 | `NewPageDialog.vue:545`、`GlobalUnlock.vue:356`、`UnlockContent.vue:137` |
| `--jg-lh-relaxed` | 1.7 | 长文阅读 / 编辑器      | `MarkdownEditor.vue:259`                                                 |

三档**各自都对上现有取值，本期零视觉变化**——行高这一步是纯"登记 + 命名"，风险最低。行高令牌一律**无单位数字**（继承时不锁死父级字号，是 CSS 最佳实践）。

### 3.3 字体栈：把权威收进 palette，让 FontSwitch 消费令牌

设计原则：**沿用 `--vp-font` / `--vp-font-heading` / `--vp-font-mono` 作为唯一契约，不另起 `--jg-font-*` 命名空间**（否则就是给"字体栈"造第二套真相，与 L0 定下的"避免维护两份真相"相悖；palette.scss 第 27 行原文就写着"本文件是设计令牌的唯一权威声明处"）。

据此做三件事：

1. **补登记 `$vp-font-mono`**（带引号字符串）。把代码字体纳入控制面，并在注释里记下这是**有意覆盖**主题默认值。
2. **把 7 套预设栈从 TS 迁进 palette**，各生成一个带引号的 `$jg-font-<key>` 令牌（`system` / `web-sans` / `misans` / `theme` / `noto-serif` / `wenkai` / `kuaile`）。其中 `system` 直接复用 `$vp-font`，**两份真相就此合一**。
3. **`fontOptions.ts` 只保留"元数据"**（`key` / `label` / 懒加载用的 `cssSheets`），`base` / `heading` 改为引用令牌 `var(--jg-font-<key>)`；`FontSwitch.vue` 的 `applyFont()` 与面板预览行都用该令牌。字体栈文本从此只有 palette 一处。

> 为什么 `base` / `heading` 引用令牌后仍然成立：`applyFont()` 里 `root.style.setProperty("--vp-font", "var(--jg-font-web-sans)")` —— 自定义属性的值允许是 `var()` 引用，主题再以 `font-family: var(--vp-font)` 消费时链式解析到真实栈。面板预览行 `:style="{ fontFamily: 'var(--jg-font-system)' }"` 同理。
> CDN 主/备（jsDelivr 主、registry.npmmirror.com 备）与"选中才懒加载"的机制**原样保留在 TS**，不受影响。

### 3.4 明确不做

- **不改主题内部字号/行高**（`node_modules`，见 2.4）。
- **不动图标字形尺寸**（见 2.5）。
- **不引入字体粗细（font-weight）刻度**。现有 `600` / `500` 等取值散落较少，且语义与字号强绑定，混在一起会把"字号刻度"这件事讲糊。留待后续。
- **不引入第三方字体/排版库**（延续自研零依赖）。
- **不引入 `<link>` 预加载或字体子集化**——改变首屏字体加载策略是性能课题，不属于"令牌化"。

## 四、实施步骤

### Step 1 — `styles/palette.scss`：新增三组令牌

- **字号**：`$jg-fs-xs`(0.75rem) / `-sm`(0.875rem) / `-base`(1rem) / `-lg`(1.125rem) / `-xl`(1.25rem)。
- **行高**：`$jg-lh-tight`(1.3) / `-normal`(1.6) / `-relaxed`(1.7)。
- **字体栈**：补 `$vp-font-mono`（带引号）；新增 `$jg-font-<key>` × 7（带引号，`system` 复用 `$vp-font`）。
- 顶部令牌维护说明补上 `L3→06` 归档指向；正文字号刻度区写明"图标字形不走本刻度"这条边界。

### Step 2 — `styles/index.scss`：正文基准接令牌

`body { font-size: 16px }` → `var(--jg-fs-base)`（零视觉变化，消除裸 px）。

### Step 3 — 组件字号收敛（12 个文件、50 处）

按 3.1 的映射逐处替换为 `var(--jg-fs-*)`；`DocEditor/` 四个文件逐处判断 `0.78/0.80` 归 `xs` 还是 `sm`。裸 px 的 `LayoutToggle.vue:103`（13px）归 `sm`。

### Step 4 — 组件行高收敛（4 处）

`FontSwitch.vue` → `tight`；`NewPageDialog.vue` / `GlobalUnlock.vue` / `UnlockContent.vue` → `normal`；`MarkdownEditor.vue` → `relaxed`。

### Step 5 — FontSwitch 接令牌

`fontOptions.ts` 删除 6 个栈常量（`SANS_STACK` 等），`base` / `heading` 改为 `var(--jg-font-<key>)`；`FontSwitch.vue` 消费逻辑保持不变（仍 `setProperty("--vp-font", ...)`），仅确认预览行能正确解析令牌。

### Step 6 — 验收与归档

浏览器实测：令牌取值、明暗两态、`getComputedStyle` 解析后的**实际 font-size**（不是只看 var 有没有）；FontSwitch 7 套切换后端到端复测（字栈真的变了、CDN 懒加载未回归）；`pnpm docs:build`；归档新建 `doc/dev-report/06-UI风格升级L3-排版与字体体系-设计与实施记录.md`。

## 五、待决策

### 决策 1：字号刻度用哪一套？

| 方案                              | 做法                                      | 利                                                               | 弊                                                                     |
| --------------------------------- | ----------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **A. 对齐 Tailwind 刻度（推荐）** | `xs 12 / sm 14 / base 16 / lg 18 / xl 20` | 刻度成比例、可心算；与用户既有技术栈心智一致；档位之间真正可区分 | `0.78~0.82` 那批单点最多 **+1.3px**（集中在 dev-only 的 `DocEditor/`） |
| B. 贴近现状微调                   | `0.75 / 0.8125 / 0.875 / 1 / 1.125`       | 视觉扰动最小（≤0.6px）                                           | 前三档步长≈1px，肉眼不可辨，刻度失去比例意义                           |
| C. 只声明令牌、不改消费方         | 令牌与字面量并存                          | 零风险                                                           | 制造"两套真相"，正是本期要清掉的债                                     |

**我建议 A**：L2 的经验是"归一化只要差值小于可辨阈值就安全"，这里最大的 +1.3px 也远小于"换个层级"的感知阈值，且重灾区是 dev-only 目录。

### 决策 2：字体栈收敛到哪一层？

| 方案                                             | 做法                          | 利                                                                                        | 弊                                                                                          |
| ------------------------------------------------ | ----------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **A. 迁进 palette，FontSwitch 消费令牌（推荐）** | 7 套栈成为 `$jg-font-*` 令牌  | 权威唯一、与"palette 是令牌唯一声明处"一致；两份真相（`SANS_STACK` × `$vp-font`）就此合一 | 多 7 个 `:root` 令牌（约 1KB CSS）；`applyFont` 写的是 `var()` 引用，比写死字符串多一层间接 |
| B. 保持现状，只加交叉注释                        | TS 与 SCSS 各留一份，注释互指 | 零改动                                                                                    | 漂移风险仍在（改一处忘另一处）                                                              |
| C. TS 为唯一权威，palette 只留 `system`          | 其余 6 套不进令牌             | 改动小                                                                                    | palette 的 `$vp-font` 仍是第二份 `system` 栈，主债未清                                      |

**我建议 A**。

### 决策 3：本期收敛范围

| 方案                | 范围                                                                                                  | 利                               | 弊                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------- | ----------------------------------------------------- |
| **A. 全量（推荐）** | `styles/` + 全部 12 个组件文件                                                                        | 一步到位，不留"新旧两套字号"并存 | 改动面最大（50 处），但绝大多数是机械替换             |
| B. 先线上、后 dev   | 本期只做 `styles/` + 线上组件（FontSwitch / LayoutToggle / LazyMermaid / ClickImagePreview / unlock） | 聚焦线上可见面                   | `DocEditor/` 四个文件 36 处裸值滞留，形成"半收敛"状态 |

**我建议 A**：`DocEditor/` 虽然 dev-only，但留着 36 处裸字号，下次再想统一刻度就得重新做一遍判断。

## 六、验收标准

1. 三组新令牌在浏览器 `getComputedStyle` 中取值正确：`--jg-fs-*` 为 `0.75/0.875/1/1.125/1.25rem`，`--jg-lh-*` 为 `1.3/1.6/1.7`，`--jg-font-<key>` 为对应字体栈（带引号的复合值**未被 `helper.inject()` 静默丢弃**——这是 L0 踩过的坑，必须逐个确认非空）。
2. 自有层（`styles/` + `components/`）**文本字号裸值命中数为 0**；唯二保留的 px 字号（`GlobalUnlock` 18px、`ClickImagePreview` 30px）**在报告中显式登记为例外**（图标字形）。
3. 自有层**文本行高裸值命中数为 0**（`GlobalUnlock` 28px / `ClickImagePreview` 38px 同样登记为图标例外）。
4. `fontOptions.ts` 中不再出现**任何字面字体栈字符串**；`--vp-font` 的默认栈文本在仓库内**只有 palette.scss 一处**。
5. FontSwitch 7 套预设端到端复测：逐套切换后 `getComputedStyle(document.body).fontFamily` **确实变化**且与预期栈首项一致；WebFont 仍为**选中才加载**（切换前不请求 CDN）；CDN 主/备回退逻辑未被破坏。
6. 暗色态回归：字号/行高令牌应为**主题无关**（明暗逐字节相同），且 `--jg-c-*` 等 map 令牌的双套机制未被破坏（对照 `--jg-c-brand`）。
7. `pnpm docs:build` 构建成功，且从 `dist` 产物中确认新令牌与字体栈**确实进入生产包**（而非只改了源码）。

## 七、风险与对策

| 风险                                 | 说明                                                   | 对策                                                                                         |
| ------------------------------------ | ------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| 字号收敛引起 dev 面板破版            | `DocEditor/` 多处 +1.3px，密集表单可能溢出             | `DocEditor` 仅在 dev serve 可见、不进构建产物；改后在编辑面板实测一轮，溢出即把该处降到 `xs` |
| 字体栈令牌被静默丢弃                 | 复合值若漏写引号 → `helper.inject()` 只 `@warn` 不报错 | 沿用 L0 的写法（外层 `"` 内层 `\"`）；验收第 1 条逐个确认非空                                |
| `var()` 引用链解析失败               | `--vp-font: var(--jg-font-web-sans)` 多一层间接        | 验收第 5 条用 `getComputedStyle(body).fontFamily` 测**解析结果**，不只看变量存在             |
| WebFont 懒加载回归                   | 改 `fontOptions.ts` 可能误伤 `cssSheets`               | `cssSheets` 原样保留；验收第 5 条检查切换前的网络请求                                        |
| 令牌与主题 `--vp-font*` 命名冲突     | 命名空间重叠                                           | 只**补** `$vp-font-mono`、不重命名已有两项，保持与主题模板的契约                             |
| 主题升级后 `--vp-font-mono` 契约变化 | 主题默认值可能变                                       | 我们已显式声明该变量，覆盖主题 `!default`，不受其取值变化影响                                |
