**系统设计** 和 **场景题** 是国内外大厂面试的高频题型，通常穿插在面试中考察求职者的综合能力——从需求分析、容量估算到架构选型，再到高并发、高可用、数据一致性的权衡。这类题目**没有标准答案**，面试官考察的是你的**思考框架**和**工程经验**。

本文先给出系统设计的作答方法论，再拆解高并发、高可用、一致性三大核心主题，最后详解短链、秒杀、排行榜、订单超时等高频场景题，帮助你建立"题目 → 知识 → 答案"的完整闭环。

## 一、作答方法论（答题框架）

无论什么场景题，都可以按下面五步展开，形成结构化回答：

### 1. 明确需求（最重要，最容易忽略）

**不要一上来就画架构**，先和面试官澄清需求：

- **功能需求**：核心功能是什么？非核心功能砍不砍？（如短链系统：生成、跳转、统计、自定义别名、过期？）
- **规模估算**：QPS 多少？数据量多少？读多还是写多？
- **可用性要求**：几个 9（99.9% / 99.99%）？能否接受短暂不可用？
- **一致性要求**：强一致还是最终一致？

> 通常可以主动假设一个量级（如"假设日活 1000w，QPS 峰值 10w"），引导面试官进入你擅长的讨论。

### 2. 容量估算（Back-of-Envelope）

- **QPS 估算**：`日活 × 人均请求数 / 86400`，再留 3~5 倍峰值系数。
- **存储估算**：`记录数 × 单条大小`，评估单机是否装得下，决定是否要分库分表、缓存、压缩。
- **带宽估算**：`QPS × 单请求响应体大小`，评估网卡瓶颈。
- 结论导向：根据量级决定是否引入缓存、消息队列、分库分表、CDN。

### 3. 架构设计

画出核心请求链路（一张时序图即可），说明每个组件的职责与选型理由：

```
客户端 → DNS/CDN → 负载均衡（Nginx）→ 网关 → 业务服务（集群，无状态）
   → 缓存（Redis）→ 数据库（MySQL 主从 + 分库分表）→ 消息队列（异步解耦）
```

### 4. 关键问题拆解

针对场景把"难点"显式说出来并给出方案：

| 难点     | 常用手段                                  |
| -------- | ----------------------------------------- |
| 高并发   | 缓存、限流、异步化、池化、水平扩容        |
| 一致性   | 事务、幂等、分布式锁、最终一致（MQ 补偿） |
| 可用性   | 冗余、降级、熔断、超时重试、故障隔离      |
| 海量数据 | 分库分表、索引优化、数据冷热分离、归档    |

### 5. 总结权衡（加分项）

最后**主动说出方案的取舍**："为了 xx 我采用了 A 方案，代价是 y；如果未来出现 z，我会演进为 B 方案"。展示工程师的权衡思维比"完整方案"更值钱。

## 二、高并发：四大核心手段

### 1. 缓存

- **作用**：把热点数据放到内存（Redis/本地缓存），扛住 90%+ 的读请求，保护数据库。
- **要点**：缓存更新策略（Cache Aside / Read Through / Write Back）、缓存穿透/击穿/雪崩的防治、缓存与数据库一致性（详见 [3 种缓存读写策略详解](/database/redis/3-commonly-used-cache-read-and-write-strategies.html)）。
- **例题**：详情页 QPS 10w，如何设计？（Redis 缓存 + 多级缓存 + CDN）

### 2. 限流

- **作用**：保护后端不被突发流量打垮。
- **算法**：计数器、滑动窗口、漏桶、令牌桶（详见 [服务限流详解](/high-availability/limit-request.html)）。
- **落地**：网关层（Nginx/Sentinel/Guava RateLimiter）限流 + 业务层兜底。

### 3. 异步化

- **作用**：削峰填谷，把非核心链路（通知、日志、统计）异步化。
- **手段**：消息队列（Kafka/RabbitMQ/RocketMQ）、线程池、延时任务。
- **例题**：订单系统写入慢怎么办？（下单写库后发 MQ，异步更新库存/发短信/扣积分）

### 4. 池化与水平扩容

- **池化**：连接池、线程池复用资源，避免频繁创建销毁。
- **水平扩容**：服务无状态化（Session 外置到 Redis），加机器即扩容量；数据库分库分表突破单机瓶颈（详见 [读写分离与分库分表](/high-performance/read-and-write-separation-and-library-subtable.html)）。

## 三、高可用：冗余、降级、熔断、幂等

- **冗余**：多副本、多机房、故障域隔离（详见 [高可用系统设计指南](/high-availability/high-availability-system-design.html)）。
- **降级**：高峰期牺牲非核心功能（如关闭推荐、评论），保住核心链路。
- **熔断**：下游故障时快速失败（Sentinel/Resilience4j），防止级联雪崩。
- **超时重试**：设置合理超时（连接/读/写），失败重试要有**退避 + 上限**（详见 [超时与重试详解](/high-availability/timeout-and-retry.html)）。
- **幂等**：重复请求不产生重复数据——靠唯一请求号 + 去重表、状态机、数据库唯一索引（详见 [接口幂等方案总结](/high-availability/idempotency.html)）。

## 四、数据一致性：事务、分布式锁与分布式 ID

- **分布式事务**：XA（强一致）、TCC、Saga、本地消息表 + MQ（最终一致）——绝大多数业务选**最终一致**（详见 [分布式事务解决方案](/distributed-system/distributed-transaction.html)）。
- **分布式锁**：Redis（SetNX + 过期时间 + Lua 续期）、ZooKeeper 临时顺序节点（详见 [分布式锁常见实现方案](/distributed-system/distributed-lock-implementations.html)）。
- **分布式 ID**：数据库自增、号段模式、雪花算法（时间戳 + 机器位 + 序列号）、UUID（详见 [分布式 ID 生成方案详解](/distributed-system/distributed-id.html)）。

## 五、高频场景题详解

### 5.1 短链系统

**需求**：长链接 → 短链接，点击跳转；可选统计、自定义别名。

**设计要点**：

1. **生成算法**：
   - **哈希取模**：`hash(longUrl) % 62` → 62 进制短码。简单，但有冲突（需加盐重算）、无法保证全局唯一且可猜测；
   - **发号器（推荐）**：全局自增 ID（号段模式/雪花）→ 62 进制编码。ID 全局唯一、不可猜测、天然有序。
2. **存储**：短码 → 长链接映射表，主键即短码；热点短链加 Redis 缓存。
3. **跳转**：HTTP 302/301 重定向。302 临时重定向利于统计（每次点击都到服务端），301 永久重定向利于浏览器缓存。
4. **防攻击**：布隆过滤器拦截不存在/过期短码，防止无效查询打爆存储。

> 关键链接：[分布式 ID 生成方案详解](/distributed-system/distributed-id.html)。

### 5.2 秒杀系统

**需求**：极短时间内海量用户抢购少量库存（如 1w 件商品 100w 人抢）。

**设计要点**（本质：削峰 + 限流 + 防超卖）：

1. **前端/网关拦截**：按钮置灰、验证码、接口限流，拦住大部分无效请求。
2. **削峰**：秒杀请求先进 MQ 排队（异步处理），系统按能力消费，防止瞬时击穿数据库。
3. **库存扣减**：**Redis 预扣库存**（`DECR` 原子操作）+ 数据库最终扣减；用 Lua 脚本保证"查库存 + 扣库存"原子性。
4. **限流**：令牌桶/滑动窗口限流，保护下单接口。
5. **防超卖**：数据库层用 `UPDATE ... WHERE stock > 0` 条件更新兜底，或乐观锁版本号。
6. **静态化 + CDN**：商品详情页静态化，扛住浏览流量。

> 关键链接：[服务限流详解](/high-availability/limit-request.html)、[3 种缓存读写策略详解](/database/redis/3-commonly-used-cache-read-and-write-strategies.html)、[分布式锁常见实现方案](/distributed-system/distributed-lock-implementations.html)。

### 5.3 排行榜

**需求**：全局 Top-N（如热榜）、实时更新、分页查询。

**设计要点**：

- **核心结构**：Redis **Sorted Set（有序集合）**——`score` 即分值，`ZADD` 实时更新，`ZREVRANGE` 取 Top-N，天然支持排序与分页（详见 [Redis 3 种特殊数据结构详解](/database/redis/redis-data-structures-02.html)）。
- **降级方案**：数据量极大时，可分区排行榜（按 uid 哈希分桶）再合并，或定时落库离线计算。
- **防刷**：结合用户维度限流、权重衰减（如 `score = 真实分 + 时间衰减项`）。

### 5.4 订单超时自动取消

**需求**：用户下单后 30 分钟未支付自动取消。

**设计要点**（三种主流方案对比）：

| 方案                                                    | 原理                                                                           | 优缺点                                                 |
| ------------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------ |
| 定时任务轮询                                            | 定期扫库，超时即取消                                                           | 简单；但不精确（取决于扫描周期）、海量订单时扫库压力大 |
| **延时队列（推荐）**                                    | 订单进入延时队列（如 Redis ZSET 按到期时间排序 / RabbitMQ 延迟消息），到期消费 | 精确、解耦；是生产最常用方案                           |
| 过期事件（如 RocketMQ 延迟消息、Redisson DelayedQueue） | 消息系统延迟投递                                                               | 依赖 MQ 能力，实现简单                                 |

> 关键链接：[Redis 延时任务详解](/database/redis/redis-delayed-task.html)、[定时任务方案详解](/system-design/schedule-task.html)、[DelayQueue 源码分析](/java/collection/delayqueue-source-code.html)。

### 5.5 Feed 流 / 信息流

**需求**：关注的人发布动态，推送给粉丝，按时间倒序展示。

**设计要点**：

- **推模式（写扩散）**：发布时写入每个粉丝的收件箱。粉丝多时写放大严重。
- **拉模式（读扩散）**：读取时拉取所有关注人的动态再合并排序。读放大，热门用户是瓶颈。
- **推拉结合（推荐）**：普通用户推，大 V 粉丝拉（大 V 的粉丝在读取时主动拉取大 V 动态），平衡读写压力。
- **存储**：Feed 内容用 MySQL/对象存储，收件箱用 Redis List/ZSET 缓存 + 分页。

### 5.6 站内消息 / IM

**需求**：实时消息推送、未读数、聊天记录。

**设计要点**：

- **实时推送**：WebSocket 长连接（详见 [Web 实时消息推送详解](/system-design/web-real-time-message-push.html)）；服务端按用户路由到对应 WebSocket 网关。
- **离线消息**：离线期间的消息落库，上线后拉取（消息队列 + 消息索引）。
- **未读数**：Redis 计数，读后清零，异步落库。
- **已读回执**：维护已读游标（如"读到第几条"），而不是逐条标记。

### 5.7 海量数据去重

**需求**：URL 去重、UV 统计、爬虫去重等，数据量十亿级。

**设计要点**：

- **精确去重**：Redis Set 去重（数据量适中）；Redis **HyperLogLog**（`PFADD`/`PFCOUNT`）用于 UV 类**近似去重**（误差约 0.81%，极省内存）。
- **大概率去重（推荐）**：**布隆过滤器**（BitMap 位数组 + 多个哈希函数）——判断"一定不在"准确，"可能存在"有误判率，内存占用极小。
- **分片**：按 uid/hash 分片存储，水平扩展。

> 关键链接：[Redis 3 种特殊数据结构详解](/database/redis/redis-data-structures-02.html)（内含 HyperLogLog、布隆过滤器）。

### 5.8 第三方授权登录

**需求**：微信/QQ/GitHub 扫码或 OAuth 登录。

**设计要点**：

- **OAuth 2.0**：授权码模式流程（跳转授权页 → 回调拿授权码 → 用授权码换 token → 用 token 换用户信息）。
- **JWT**：无状态令牌（Header.Payload.Signature），用于跨服务认证，注意过期与续期。
- **本地账号绑定**：第三方 openid + 本地用户表映射，避免一个第三方账号一个本地账号的重复注册。

> 关键链接：[认证授权基础](/system-design/security/basis-of-authority-certification.html)、[JWT 详解](/system-design/security/jwt-intro.html)。

## 六、面试加分建议

1. **主动澄清需求**：一句"我先确认几个量级问题"就能体现专业性。
2. **先说结论再展开**：如"核心是缓存 + 异步 + 限流三件事"。
3. **画图 + 写伪码**：白板画链路图、写关键伪代码（如扣库存的 Lua 脚本）。
4. **主动提权衡**："这个方案牺牲了实时性，但换来了吞吐，符合本场景"。
5. **关联已知系统**：提到自己项目里真实踩过的坑（如"我们之前就是没做限流被打挂了"），远比背诵方案有说服力。
