## 作答框架

遇到系统设计题，建议按以下框架作答：

1. **明确需求**：先向面试官确认核心功能、QPS/数据量、可用性要求（避免答偏）。
2. **容量估算**：估算请求量、存储量、带宽，判断是否需要分库分表/集群。
3. **架构设计**：画出一条核心请求链路，说明每个环节用什么组件解决什么问题。
4. **关键问题**：高并发（缓存/限流/异步）、一致性（事务/幂等/最终一致）、可用性（降级/熔断/冗余）。
5. **总结权衡**：说明方案的取舍与改进方向。

## 高频场景题精讲（答题要点）

下面每道题按「考察点 → 答题主线 → 关键取舍 → 常见追问」展开。面试时的正确姿势是：**先用自己的话讲主线，再讲取舍，最后等面试官挑细节追问**，不要一上来就堆组件名。

### 如何设计一个秒杀系统？

**考察点**：高并发写入削峰、库存超卖、防刷、系统可用性。

**答题主线**：

1. 接入层：静态资源走 CDN、按钮置灰防重复提交、验证码/答题削峰、IP 维度限流。
2. 网关层：限流（单机 + 分布式）、黑名单、请求合法性校验，把无效流量挡在最外层。
3. 服务层：Redis 预扣库存（Lua 脚本保证"判断 + 扣减"原子性）、库存分桶、异步下单。
4. 存储层：MQ 异步落库、订单状态机、最终一致性 + 补偿。

**关键取舍**：

| 取舍点   | 方案 A                | 方案 B         | 建议                              |
| -------- | --------------------- | -------------- | --------------------------------- |
| 库存扣减 | Redis 预扣 + 异步落库 | 数据库直接扣减 | 秒杀选前者，后者撑不住瞬时并发    |
| 削峰方式 | MQ 异步下单           | 线程池排队     | MQ 更稳，可限速、可回放、可重试   |
| 防超卖   | Lua 原子扣减          | 分布式锁       | 高并发下 Lua 更轻，锁容易成为瓶颈 |

**常见追问**：Redis 扣了库存但订单创建失败怎么办？（补偿回滚库存、MQ 重试 + 幂等）如何防止一个人抢多单？（用户维度限购 + 去重表）

### 如何设计一个短链系统？

**考察点**：短码生成、冲突处理、跳转性能、点击统计。

**答题主线**：长链接 → 唯一短码 → 存储映射（MySQL + Redis 缓存）→ 跳转 → 点击统计（异步）。

**关键取舍**：

- **301 还是 302**：301 永久重定向能被浏览器缓存、服务端压力小，但统计不到后续点击；302 每次都回源，可以统计。要统计就用 302。
- **哈希取模还是发号器**：哈希取模会冲突，需要处理冲突或加盐重试；发号器（Redis INCR、Snowflake）无冲突，但短码连续可被遍历猜测，需要加盐混淆。

**常见追问**：短码长度怎么定？（62 进制约 6 位可容纳 568 亿）如何防遍历？（加盐、限频、校验签名）

### 40 亿个 QQ 号，限制 1GB 内存，如何去重？

**考察点**：容量估算能力、位图/布隆过滤器/分治的取舍。

**答题主线**：

1. **先算容量**：40 亿个 32 位整数本身约 16GB，1GB 内存装不下原始数据，必须做位级压缩或分治。
2. **首选位图**：40 亿 ≈ 2^32，若编号是 32 位无符号整数，位图需要 `2^32 / 8 = 512MB`，1GB 内存放得下，一次遍历即可去重，时间复杂度 `O(n)`。
3. **编号范围更大时**：10 位 QQ 号可达 10^10 量级，位图需要约 1.25GB，超出 1GB，此时改用分治（按哈希取模拆成多个文件，逐个文件内存去重后合并）。
4. **布隆过滤器要慎选**：它只判断"可能存在/一定不存在"，40 亿元素在 1% 误判率下需要约 4.8GB，1GB 内做不到低误判，且它不能输出元素本身，只能用于判重而不是去重。

**常见追问**：位图和布隆过滤器的区别？（位图精确、空间随值域增长；布隆有误判、空间随元素数增长）分治时如何保证同一元素落到同一份？（用哈希而不是随机）

### 如何解决大文件上传问题？

**考察点**：分片、断点续传、秒传、并发控制。

**答题主线**：

1. 前端计算文件唯一标识（文件名 + 大小 + 修改时间，或分片 MD5 汇总）。
2. 上传前先查询该标识是否已存在 → 命中即**秒传**。
3. 按固定大小切片（如 5MB），并发上传，服务端记录每个分片的上传状态。
4. 中断后重新进入，查询已上传分片 → **断点续传**，只补缺失分片。
5. 分片全部到齐后合并，并校验整体 MD5 保证完整性。

**关键取舍**：合并放服务端自己拼（实现简单，但吃服务端 IO）还是用对象存储的分片上传 API（如 S3 Multipart，更省心，推荐）；分片大小取大一点能减少请求数，但单片失败要重传的成本更高。

**常见追问**：如何避免重复合并？（合并状态机 + 唯一索引）秒传会不会被滥用？（做权限校验，只有已授权的文件才允许秒传）

### 接口幂等如何实现？

**考察点**：幂等的本质、与并发的区别、方案选型。

幂等的定义是：**同一个请求执行一次和执行多次，对系统产生的影响相同**。它解决的是"重复请求"，不是"并发冲突"。

| 方案                       | 适用场景                     | 注意点                                   |
| -------------------------- | ---------------------------- | ---------------------------------------- |
| 唯一索引 / 去重表          | 创建类操作                   | 最简单可靠，让数据库兜底                 |
| Token 机制                 | 表单提交                     | 先申请 token，提交时校验并删除，一次有效 |
| 状态机                     | 订单、支付等有明确状态的业务 | 只允许合法状态流转，非法流转直接拒绝     |
| 乐观锁（version）          | 更新类操作                   | 并发冲突会失败，需要重试或提示           |
| Redis SETNX 记录 requestId | 高频接口                     | 需要设置合理的过期时间                   |

**常见追问**：支付场景怎么做幂等？（订单号 + 唯一索引 + 状态机，同时依赖支付渠道侧的幂等能力）幂等和分布式锁有什么区别？（幂等保证"重复执行无副作用"，锁解决"同时执行互斥"）

### 服务限流怎么做？

**考察点**：限流算法对比、单机与分布式、限流之后的处理。

| 算法         | 特点                     | 局限                             |
| ------------ | ------------------------ | -------------------------------- |
| 固定窗口计数 | 实现最简单               | 窗口切换处可能放过 2 倍流量      |
| 滑动窗口     | 比固定窗口平滑           | 需要维护时间片，实现更复杂       |
| 漏桶         | 输出速率恒定，流量最平稳 | 抗突发能力差                     |
| 令牌桶       | 允许一定突发流量，最常用 | 需要维护令牌生成速率             |
| 滑动日志     | 精度最高                 | 要存每次请求的时间戳，内存开销大 |

- **单机限流**：Guava `RateLimiter`、Sentinel 单机流控。
- **分布式限流**：Redis + Lua（令牌桶/滑动窗口），或直接交给网关（Spring Cloud Gateway 的 `RequestRateLimiter`、Nginx `limit_req`）。
- **被限流之后**：快速失败返回 429 或业务提示、排队等待、降级返回兜底数据。

**常见追问**：为什么通常用令牌桶而不是漏桶？（允许突发流量）Redis 限流如何保证原子性？（Lua 脚本把"读 + 判断 + 写"合成一次原子操作）

### 订单超时自动取消怎么实现？

| 方案                            | 精度   | 可靠性                           | 适用场景             |
| ------------------------------- | ------ | -------------------------------- | -------------------- |
| 定时任务轮询                    | 分钟级 | 高                               | 数据量小、精度要求低 |
| JDK `DelayQueue`                | 高     | 低（单机、重启丢失）             | 单机小规模           |
| Redis ZSet（score = 到期时间）  | 秒级   | 中                               | 中小规模，实现简单   |
| Redis 过期事件监听              | 秒级   | **低**（pub/sub 不持久，可能丢） | 不推荐用于核心业务   |
| MQ 死信队列 / TTL               | 秒级   | 高                               | 推荐，可重试可回放   |
| 时间轮（如 `HashedWheelTimer`） | 毫秒级 | 中（内存态）                     | 大规模单机高效计时   |

**常见追问**：ZSet 方案如何避免重复消费？（取到到期任务后先删除成功再处理，或加分布式锁 + 状态判断）为什么不用 Redis 过期事件？（key 过期事件基于发布订阅，不持久化、网络抖动就会丢，核心业务不能依赖）

### 如何设计一个排行榜？

核心是 Redis ZSet：`ZADD` 更新分数、`ZREVRANGE` 取前 N、`ZREVRANK` 查名次、`ZINCRBY` 累加。

- **分榜**：日榜 / 周榜 / 总榜用不同的 key，定时合并。
- **分片**：单榜成员上百万会形成大 key，可按用户 ID 哈希分片，查询时归并各分片结果。
- **取舍**：每次业务操作都写 Redis 实时性最好但压力大；也可以定期批量聚合后写入，牺牲一点实时性换取吞吐。

**常见追问**：分数相同怎么排名？（Redis 按成员字典序作为二级排序，需要自定义时把次要因子编码进 score 的小数位）大 key 怎么治理？（分片、拆榜、设置过期）

### 如何统计网站 UV？

- **PV**：直接用 Redis `INCR` 累加即可。
- **UV**：
  - `Set` 存用户 ID：精确，但用户量大时内存开销高。
  - `HyperLogLog`：12KB 固定开销、标准误差 0.81%，推荐。
  - 布隆过滤器：只能判断"在不在"，不能计数，不适合 UV 统计。

**常见追问**：HyperLogLog 能精确去重吗？（不能，是概率算法，估算值有误差）多天 UV 如何合并？（`PFMERGE` 合并多个 HLL 结构，不需要重新遍历明细）

### 如何设计一个站内消息系统？

**答题主线**：

1. **消息模型**：点对点消息、群发消息分开建模，群发只存一份消息 + 一份收件人关系。
2. **未读数**：用计数表或 Redis 计数器维护，不要每次 `count(*)`。
3. **推送通道**：在线走 WebSocket 长连接，离线转 App 推送。
4. **可靠性**：消息表 + 已读状态，客户端拉取时用游标分页弥补推送丢失。

**常见追问**：未读数怎么保证准确？（计数与消息表在同一事务里更新，或用定时任务校正）长连接多实例如何路由？（网关维护 uid → 节点 的路由表，存在 Redis 里）

### 如何设计微博 Feed 流 / 信息流系统？

| 模式             | 做法                       | 优点     | 缺点                    |
| ---------------- | -------------------------- | -------- | ----------------------- |
| 推模式（写扩散） | 发布时写入所有粉丝的收件箱 | 读极快   | 大 V 发一条要写几百万次 |
| 拉模式（读扩散） | 读时聚合所有关注人的发件箱 | 写极快   | 读慢，需要多次查询归并  |
| 推拉结合         | 普通用户推、大 V 拉        | 兼顾两者 | 实现复杂，需要判断阈值  |

**常见追问**：收件箱存哪里？（Redis List/ZSet 按时间倒序，只保留最近 N 条）多个来源怎么合并？（按时间做归并排序取前 N）

### 多位骑手抢一个订单如何保证不重复？

**答题主线**：Redis `SETNX` 抢锁降低并发 → 数据库唯一索引（订单号 + 骑手号）兜底 → 状态机保证订单只能被接单一次。

**常见追问**：锁到期自动释放了怎么办？（看门狗续期，同时靠数据库唯一约束最终兜底）为什么最终一定要有数据库约束？（Redis 锁只能降低并发冲突概率，不能作为一致性的最终保障，锁失效、主从切换都可能让两个请求同时通过）

### 如何实现第三方授权登录？

OAuth 2.0 授权码模式的完整流程：

1. 前端跳转到授权页（带上 `client_id`、`redirect_uri`、`state`）。
2. 用户同意后回调你的服务，带上一次性 `code`。
3. **后端**用 `code` + `client_secret` 去换 `access_token`。
4. 用 token 拉取用户信息，本地建号或绑定已有账号。
5. 签发自己的会话（JWT 或 Session），后续请求不再依赖第三方 token。

**关键点**：`client_secret` 只能保存在后端，绝不能下发到前端；`state` 参数用于防 CSRF；`code` 一次性且短期有效；回调地址必须做白名单。

**常见追问**：为什么不直接返回 token？（避免 token 出现在浏览器地址栏、历史记录和 Referer 里）三方登录后如何和已有账号打通？（手机号/邮箱匹配 + 用户主动绑定确认）

### 如何安全传输和存储密码？

- **存储**：绝不明文存储，也不要用可逆加密。正确做法是加盐哈希，优先选择 bcrypt / scrypt / Argon2 这类"慢哈希"（自带盐、计算成本可调），PBKDF2 次之。
- **传输**：全站 HTTPS，登录接口加图形验证码或短信验证防撞库，连续失败要做限制。
- **脱敏**：日志和返回体里不能出现明文密码或完整手机号。

**常见追问**：为什么 MD5 加盐也不够？（GPU 每秒可算上百亿次，慢哈希才能把单次校验成本拉高）算法升级怎么平滑迁移？（登录时用旧算法校验通过后，立刻用新算法重新存储）

### 项目敏感词脱敏是如何实现的？

- **过滤**：用 DFA（Trie 前缀树）扫描，复杂度只与文本长度有关，与词库规模基本无关；词库很大时用 AC 自动机做多模式串匹配。
- **脱敏**：姓名保留姓氏、手机号保留前 3 后 4、身份证保留首尾、邮箱只保留首字符；规则要可配置，避免硬编码。

**常见追问**：如何避免误伤正常词？（词库分级 + 白名单）用户用火星文、拼音、谐音绕过怎么办？（先把文本归一化——全半角、繁简、拼音转换——再做匹配）

### 如何设计一个动态线程池？

**答题主线**：

1. **参数外置**：核心/最大线程数、队列容量、空闲存活时间、拒绝策略全部放到配置中心或数据库，支持运行时刷新。
2. **监控告警**：采集活跃线程数、队列长度、拒绝次数、任务耗时，超阈值告警。
3. **自定义拒绝策略**：拒绝的任务落盘或投递到 MQ 异步补偿，而不是直接静默丢弃。
4. **优雅停机**：`shutdown()` + `awaitTermination()`，保证在途任务执行完。
5. **线程池隔离**：按业务拆分线程池，避免一个业务打满影响其他业务。

**常见追问**：为什么不用 `Executors` 的预设线程池？（`newFixedThreadPool` 用无界队列会 OOM，`newCachedThreadPool` 线程数无上限）动态调整的核心线程数为什么能立刻生效？（`ThreadPoolExecutor` 在 `execute` 时会读取最新参数，但缩小核心线程数需要配合 `allowCoreThreadTimeOut`）

## 容量估算速查

系统设计题几乎都会问"这个量级怎么算"，下面几个公式够用：

| 指标     | 估算方式                                               |
| -------- | ------------------------------------------------------ |
| 平均 QPS | `DAU × 人均请求数 / 86400`                             |
| 峰值 QPS | 平均 QPS × 2~5（具体倍数看业务形态，秒杀、抢购要更高） |
| 存储容量 | 记录条数 × 单条大小 × 副本数 × 保留时长                |
| 出口带宽 | 峰值 QPS × 单次响应字节数                              |
| 缓存容量 | 热点数据量 × 单条大小，再按经验留 20%~30% 余量         |

**举个例子**：1000 万 DAU、人均 20 次请求，则平均 QPS ≈ `1000 万 × 20 / 86400 ≈ 2314`，按 4 倍峰值估算约 `9200`。这个量级下单机 MySQL 写库会紧张，需要引入缓存和分库分表。
